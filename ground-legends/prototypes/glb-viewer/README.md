# GLB 선수 모델 뷰어 (프로토타입)

외부 3D 선수 모델(스킨드 GLB/glTF)을 Ground Legends에 쓸 수 있을지 확인하는 단독 페이지입니다.

- 본 게임(`ground-legends/index.html`)과 웹사이트 사본(`ground-legends/docs/index.html`)은 이 폴더를 불러오지 않습니다.
- 이 폴더도 게임 코드를 불러오지 않습니다.
- 게임의 선수는 바뀌지 않습니다.

## 실행

`file://`로 직접 열면 브라우저가 `models/`의 GLB를 읽지 못합니다. 간단한 웹 서버로 엽니다.

```sh
cd ground-legends/prototypes/glb-viewer
python3 -m http.server 8000
# 브라우저에서 http://localhost:8000/
```

- 열면 `models/Xbot.glb`를 자동으로 불러옵니다. `?autoload=0`을 붙이면 자동으로 불러오지 않습니다.
- 다른 파일은 주소 칸에 경로를 넣거나, 파일 선택 또는 끌어다 놓기로 엽니다.
- 끌어다 놓기는 GLB 한 파일만 됩니다. 텍스처가 따로 있는 `.gltf`는 웹 서버 경로로 엽니다.
- three.js 본체는 게임과 같이 cdnjs에서 받습니다. 첫 실행에는 인터넷이 필요합니다.

### 화면

- **상태 줄**: 불러오는 중, 진행률, 실패 이유를 보여 줍니다. 같은 내용이 콘솔에도 찍힙니다.
- **보정**
  - 키: 기본 1.8 m. 스킨이 입혀진 정점 기준입니다.
  - 방향: 자동, 또는 0/90/180/270°. 모델 정면을 게임과 같은 +z로 돌립니다.
  - 발을 바닥(y=0)에 맞춤.
  - 제자리 재생: 루트 트랙의 수평 순이동을 뺍니다.
- **클립 표**
  - 이름, 길이, 트랙 수, 루트 모션, 트랙이 가리키는데 모델에 없는 뼈를 보여 줍니다.
  - 클릭하면 전환 시간만큼 크로스페이드하며 바꿉니다.
  - 같은 클립을 다시 누르면 아무것도 하지 않습니다.
  - 액션은 한 번 만든 것을 다시 씁니다.
- **게임 위치 따라가기**: 게임 로직이 정한 위치와 방향을 모델이 따라가는 흉내입니다. 원을 돕니다.
  - 바깥 그룹(holder)이 위치와 방향을 갖고, 모델은 그 자식입니다.
  - 애니메이션은 모양만 바꾸고 위치는 바꾸지 않습니다.
- **선수 수**: 1, 11, 22, 44. 성능을 비교하는 데 씁니다.
- **HUD**: 그리기 호출, 삼각형, `renderer.render` 시간을 보여 줍니다.
- **카메라**: 드래그로 돌리고 휠로 확대합니다. 따로 라이브러리를 쓰지 않습니다.
- **매 프레임**: 선수마다 `mixer.update(dt)`를 한 번 부릅니다. `dt`는 0.05초로 자릅니다. 게임의 `frame`과 같습니다.

### 헤드리스 점검

```sh
cd ground-legends/prototypes/glb-viewer
node check.js                 # models/의 모든 GLB
node check.js Soldier.glb     # 하나만
```

- Playwright, three r128의 위치는 `../../tests/legacy/paths.js`를 따릅니다. `ground-legends/tests/README.md`를 보세요.
- 모델마다 다음을 JSON으로 찍습니다.
  - 불러온 결과: 메시, 뼈, 재질, 텍스처, 삼각형, 키, 배율, 방향
  - 클립별 정보: 루트 모션, 발 관절 최저 높이, 제자리 재생 때 엉덩이가 holder에서 벗어난 최대 거리
  - 클립 전환 때 한 프레임 동안 뼈가 가장 크게 움직인 거리
  - 선수 1명과 22명일 때의 그리기 호출, 삼각형, 렌더 시간
- `out/`에 스크린샷을 남깁니다.
- 불러오기 실패나 콘솔 오류가 있으면 `CHECK FAIL`을 찍고 종료 코드 1로 끝납니다. 없으면 `CHECK PASS`와 종료 코드 0입니다.
- 스크린샷 실패는 결과의 `screenshot` 칸에 적습니다.

## 사용자가 받아야 하는 파일

이 환경에서는 itch.io, quaternius.com, opengameart.org, Mixamo, mocap.cs.cmu.edu에 연결할 수 없었습니다. 프록시가 연결을 거절했고(403), WebFetch는 DNS 오류를 냈습니다. GitHub 공개 저장소만 받을 수 있었습니다. 그래서 아래 파일은 아직 열어 보지 못했습니다.

1. Quaternius Universal Base Characters: `quaternius.itch.io` 또는 `quaternius.com`. glTF/GLB 판이 있으면 그것을 받습니다.
2. Quaternius Universal Animation Library (Standard 무료판): 같은 곳.
   - 두 팩에 킥이나 축구 동작이 있는지는 확인하지 못했습니다. 검색으로 본 설명에는 이동, 달리기, 밀기, 기어가기, 수영, 앉기, 사망, 근접 콤보, 파쿠르 등만 나옵니다. 동작 목록은 `https://quaternius.com/animviewer.html`에서 볼 수 있다고 합니다.
3. Mixamo: 축구 동작이 있는지와 정확한 이름은 확인하지 못했습니다. 검색에 Mixamo 공식 목록이 나오지 않았습니다.
   - Adobe 계정으로 mixamo.com에 들어가 "soccer", "kick", "header", "goalkeeper", "tackle"로 검색합니다.
   - Xbot이나 Soldier 대신, 라이선스가 확인된 캐릭터(예: Mixamo 기본 캐릭터)에 적용해 FBX로 받습니다. Blender에서 GLB로 바꿉니다.
   - 받은 파일은 `models/mixamo/`에 둡니다. 위 표처럼 원본 파일은 저장소에 커밋하지 않습니다.

받은 파일을 `models/`에 넣고 `node check.js 파일이름.glb`를 실행하면 아래 표와 같은 항목이 나옵니다. 그 결과로 뼈 이름, 방향, 루트 모션을 확인한 뒤에 리타게팅 범위를 정합니다.

## 점검 결과 (이 환경, 2026-10-26)

`node check.js` 결과는 `CHECK PASS`, 종료 코드 0이었습니다. 콘솔 오류와 실패한 요청은 없었습니다.

|---|---|---|---|---|---|---|---|---|
| CesiumMan | 1 | 19 | 1 (1024² 텍스처) | 4,672 | 1.507 m | 1.1944 | 0° | `animation_0` 2.0 s (걷기) |
| Soldier | 2 | 49 (`mixamorig`) | 2 (1024² 색, 노멀) | 11,376 | 1.832 m | 0.9825 | 180° | Idle 1.967, Run 0.7, TPose 0.033, Walk 1.033 s |
| Xbot | 2 | 67 (`mixamorig`) | 2 (텍스처 없음) | 49,112 | 1.809 m | 0.995 | 0° | agree 1.833, headShake 2.567, idle 2.5, run 0.7, sad_pose 0.067, sneak_pose 0.067, walk 0.967 s |

- **루트 모션**
  - 엉덩이 뼈의 세계 좌표를 클립 동안 31번 측정했습니다.
  - 순이동이 0.1 m를 넘거나 최대 이동이 0.25 m를 넘으면 "있음"으로 봅니다.
  - 있음은 Xbot `sneak_pose`(0.146 m, 2키 포즈 클립)뿐입니다.
  - 걷기와 달리기는 모두 제자리 클립입니다. Soldier Walk의 흔들림은 최대 0.054 m입니다.
- **Soldier 뼈 누락**: 클립 4개 모두 트랙 3개가 모델에 없는 손가락 끝 뼈(Pinky3, Thumb3 등)를 가리킵니다.
  - three.js는 그 트랙만 건너뜁니다.
  - 화면에서 문제는 보이지 않았습니다.
- **발 관절 최저 높이**: 관절 기준이며 신발 바닥 기준이 아닙니다.
  - Soldier: 0.008–0.014 m.
  - Xbot: −0.010–0.003 m. 관절이 바닥 아래로 조금 내려가며, 발바닥이 땅에 박혀 보일 수 있습니다.
  - 휴지 자세를 `skeleton.pose()` 대신 파일의 뼈 변환으로 바꾼 뒤(아래 BVH 절) 바닥 맞춤이 3 mm쯤 달라졌습니다. 고치기 전 측정은 −0.013–0 m였습니다.
- **제자리 재생 때 엉덩이와 holder 사이 거리**: Xbot walk는 0.138 m, Soldier Walk는 0.069 m입니다.
  - 순이동 때문이 아닙니다. 그 클립에서 엉덩이가 모델 원점보다 앞에 있기 때문입니다.
  - idle에서 walk로 바뀌면 몸이 10 cm 남짓 앞으로 옮겨 보입니다.
- **클립 전환 때 한 프레임 최대 뼈 이동**
  - Soldier Idle→Run: 평소 0.001 m, 0.25 s 크로스페이드 0.098 m, 즉시 전환 0.616 m.
  - Xbot agree→headShake: 0.008 / 0.007 / 0.043 m.
  - 즉시 전환은 눈에 띄게 튀므로 크로스페이드가 필요합니다.

### 성능 (측정 환경을 같이 적음)

- **측정 환경**
  - 헤드리스 Chromium(Playwright 1.56.1), SwiftShader 소프트웨어 WebGL, 1100×700 창.
  - GPU 없음. 클라우드 컨테이너.
  - 렌더 시간은 `renderer.render` 호출 20번의 CPU 시간 중앙값입니다. FPS가 아니며, 실제 GPU 기기의 수치도 아닙니다.
- 아래 표의 수치는 `out/check.log`의 마지막 실행 결과입니다. 렌더 시간은 실행마다 1–2 ms 달라졌습니다.

### 옮기는 방법 (`retarget.js`)

- **뼈 대응**: CMU 22개를 Mixamo 이름 뼈 22개에 맞춥니다.
  - Hips→Hips, LowerBack→Spine, Spine→Spine1, Spine1→Spine2, Neck→Neck, Head→Head.
  - 어깨, 팔, 다리, 발, 발가락은 같은 이름끼리 맞춥니다.
  - 대응하지 않는 소스 뼈: LHipJoint, RHipJoint, Neck1, 손가락.
  - 대상에서 소스가 없는 뼈(Xbot 45개: 손가락, Neck 위 등)는 휴지 자세를 유지합니다.
- **기준 자세**: 양쪽 휴지 자세를 비교합니다.
  - 소스는 변환본이 0번 프레임에 넣은 T-pose입니다.
  - 대상은 파일이 준 뼈 변환입니다.
  - 뼈마다 휴지 대비 회전 변화를 대상 휴지 회전에 곱합니다. 소스와 대상의 휴지 뼈 방향 차이도 보정합니다.
- **방향**: 타격 순간 차는 발끝의 수평 진행 방향을 대상의 정면(+z)에 맞춥니다. 그래서 측정의 "타격 방향"이 0°에 가까운 것은 검증 결과가 아니라 맞춘 결과입니다. 그 대신 타격 순간 골반이 향하는 방향을 따로 잽니다.
- **엉덩이 위치**: 다리 길이 비율로 줄입니다(Xbot 0.0559).
  - 제자리판은 엉덩이 수평 경로에서 ±0.25초 이동 평균을 빼서 만듭니다. 걸음은 지우고 흔들림은 남깁니다.
  - 원래판에는 도움닫기 이동이 그대로 남아 있습니다(루트 모션 1.1–1.9 m).
- **바닥**: 대상 모델에서 클립을 실제로 재생해 맞춥니다. 스킨 정점 최저점의 하위 20% 값이 바닥에 오도록 엉덩이 높이를 옮깁니다.
- **킥 구간**: 발끝 속도가 가장 큰 프레임을 타격으로 봅니다. 그 0.6초 전부터 0.5초 후까지를 60 fps로 다시 샘플합니다.
- **트랙**: 모든 뼈에 회전, 위치, 배율 트랙을 넣습니다(Xbot 201, Soldier 147). 파일의 기존 클립과 같은 방식입니다.
- **재생**: 타격이 있는 클립은 한 번 재생하고 마지막 자세를 유지합니다(LoopOnce, clamp).

리타깃을 만들면서 찾은 기존 뷰어 결함이 있습니다.
- `skeleton.pose()`는 Xbot 같은 Mixamo 파일에서 뼈를 bind 공간에 남깁니다. 그러면 Armature의 0.01 배율 아래에서 크기가 100분의 1이 됩니다.

- 이제 휴지 자세는 불러올 때 저장한 뼈 변환으로 돌립니다.

### 좌표와 앞선 값의 정체

- 모든 값은 holder 좌표(게임의 `p.pos`와 방향: +z 정면, +x 선수의 왼쪽)이고 단위는 m입니다.
  - 첫 선수의 holder는 원점에 정면 +z로 있으므로 세계 좌표와 같습니다.
- 앞 단계의 "발과 공 사이 0.67–0.86 m"는 다음 조건에서 잰 값입니다.
  - 제자리판 클립의 발끝 최고속 프레임(클립 0.600 s)
  - `RightToeBase` 관절(발볼)에서 가정한 공 중심 (0, 0.11, 0.5)까지의 거리
  - 관절과 공 중심 사이 거리이지, 표면 사이 거리가 아닙니다.
  - 그 프레임의 발끝 관절은 z=0.05 m라서, 공 깊이(0.5 m)까지 아직 0.45 m 남아 있었습니다.
- 이번에는 발 표면과 공 표면 사이 거리(gap)를 씁니다.
  - 오른발 뼈를 주로 따르는 스킨 정점 중 공 중심에 가장 가까운 점까지 거리에서 0.11을 뺀 값입니다.
- 방향 정렬과 위치 정렬은 따로 봅니다.
  - 리타깃이 발끝 최고속 프레임의 진행 방향을 +z로 돌렸습니다. 이것은 방향 정렬입니다.

  - 위치는 전혀 맞춰져 있지 않았습니다.

  1. 제자리판은 타격 중 디딤발이 0.28 m(게임 구간 0.13–0.15 m) 미끄러집니다.
     - 원래판은 0.01–0.02 m이지만, 몸이 게임 위치에서 흘러갑니다.
     - 게임 선수가 슛 중 약 1.3 m/s로 움직이면 원래판이 거의 맞습니다(앞뒤 변화 0.2 m).
  2. 게임은 공 출발 0.233 s 전에야 킥을 시작합니다. 그래서 0.55–0.66 m 오프셋을 넣을 시간이 부족합니다.
     - 0.25 s 페이드면 접촉에 대기 자세가 섞이고, 0.15 s면 4–5 m/s로 미끄러집니다.
  3. 팔로스루에서 디딤발이 2 cm 묻힙니다.
- **다음 조치 제안** (모두 게임 통합 전 프로토타입에서)
  1. 원래판(CR) 구간과 "게임 이동 속도 = 원본 이동 속도"를 함께 쓰는 설계를 뷰어의 "게임 위치 따라가기"로 시험합니다. 이것은 게임이 슛 중 선수를 어떻게 움직일지의 문제라 승인이 필요합니다.
  2. 오프셋을 D 누름(차지) 순간부터 키우는 방식을 시험합니다.
  3. 디딤발 접지(발 IK 또는 구간별 바닥 맞춤)를 고칩니다.
  4. 방향 정렬을 최고속 프레임이 아니라 접촉 프레임 기준으로 바꿉니다(지금 6–11° 차이).

## 디딤발 안정화와 접촉 정렬 (게임 타임라인, `check_kick.js` 2단계)

### 게임이 슛 중에 선수를 어떻게 움직이는가 (코드와 실측)

- **코드**
  - D를 누르는 동안과 D를 뗀 뒤 공이 떠나기 전까지 `wantVel = 정면 × min(현재 속도, 최대 속도의 30%)`입니다(3795–3796).
  - 감속은 최대 17 m/s²입니다(3126). 공이 떠난 뒤에는 입력대로 움직입니다.
  - 서 있으면 계속 서 있고, 달리고 있었으면 최대 속도의 30%(이 선수 2.36 m/s)까지 줄어든 채 계속 갑니다.
- **실측**: `check_kick.js`가 게임 페이지를 하네스로 그대로 열고(수정 없음) 틱마다 선수와 공 위치를 기록합니다.

| 상황 | D 누름→공 출발 | 그동안 선수 이동 | 공 출발 직전 공 위치 (선수 앞) | 공 출발 뒤 0.30 s 이동 |
|---|---|---|---|---|
| 서서, D 0.1 / 0.2 / 0.3 s | 0.333 / 0.433 / 0.533 s | 0 m | 0.50 m | 0 m |
| 5.5 m/s로 달리다, D 0.1 / 0.2 / 0.3 s, 방향키 뗌 | 같음 | 0.81 / 1.01 / 1.20 m | 0.45 / 0.49 / 0.43 m | 0.12 m |

- 모든 경우에 공은 키를 처리한 틱에서 14틱 뒤에 떠납니다(게이트로 확인).
- 방향키를 계속 누르면 공 출발 뒤 다시 가속합니다. 앞 단계 측정에서 0.30 s에 1.11 m였습니다.
  - 이번 비교에는 넣지 않았습니다. 이 경우 킥이 끝난 뒤 선수가 바로 달려 나가므로, 복귀 전환이 대기가 아니라 달리기가 됩니다.

### 비교한 방법 (모두 D 누름 = 0 s, 게임 위치와 공은 위 실측값)

- 공통 조건
  - 접촉: 공 출발 직전 틱(키 틱 + 13틱)에 접촉하도록 클립 시간을 맞춥니다.
  - 전환: 대기(서서) 또는 달리기(달리다)에서 킥으로 0.15 s 크로스페이드합니다. 게임의 킥 포즈가 끝나는 공 출발 + 0.30 s부터 대기로 0.25 s 크로스페이드합니다.
  - 오프셋: 모델(루트)을 게임 선수 위치에서 옮기는 양입니다. 킥의 가중치를 따라 커지고 작아집니다.
- 방법
  - **A**: 제자리판. 킥은 D 누를 때 시작합니다. 오프셋은 D 누름부터 디딤 착지까지 커집니다(앞 단계의 D).
  - **B**: 제자리판. 오프셋이 D 누름부터 접촉까지 커집니다.
  - **C**: 제자리판. 킥 클립을 D 뗄 때(게임의 킥 포즈 시작) 시작합니다. 오프셋도 그때부터 접촉까지 커집니다.
  - **D**: 원래판(원본 이동 유지). 오프셋은 없습니다. 비교 기준입니다.
  - **E**: 원래판.
    - 처음에는 원본 이동의 평활 경로를 빼서, 제자리판처럼 골반이 선수 위에 있게 합니다.
    - D 누름부터 디딤 착지까지, 접촉 때 공에 닿는 월드 고정 위치로 옮겨 갑니다.
    - 디딤 착지 뒤에는 게임 선수가 움직인 만큼 오프셋에서 빼서, 모델이 월드에 그대로 있게 합니다.
  - **E2**: E + 클립 접지 보정. 발가락을 굽히고, 남는 만큼 골반을 높입니다(아래).
  - **E3**: E2 + 전환 중 접지. 섞인 자세가 발을 땅에 묻으면 그 프레임만큼 모델 전체를 올립니다.

### 접촉 프레임 (유지)

- 접촉은 발끝 최고속 프레임이 아니라, 그 근처에서 발끝이 가장 낮은 순간(Xbot 클립 0.6158 s, Soldier 0.6075 s)입니다.
- 근거: 소스 120 Hz에서 최고속 +0.017 s에 발끝이 가장 낮고, +0.025 s부터 급감속합니다.
- CMU에는 공이 없으므로 이것은 추정입니다.
- 거리는 두 가지를 구분합니다. 공 중심까지 거리는 `ballCentre`, 발 표면에서 공 표면까지 거리는 gap입니다.
- 타격 방향은 접촉 프레임 기준으로 잽니다. Xbot 정면에서 10.6° 왼쪽·3.1° 위, Soldier 6.0° 왼쪽·1.1° 아래입니다.

  - 발가락 굽힘 뒤 발가락 외 뼈 이동 ≤ 0.1 mm
  - 굽힘 ≤ 원본 그 발의 발가락 움직임 폭
  - 발가락 + 골반 보정 뒤 침하 ≥ 한도
  - 골반 상하 이동이 보정 전 + 2 mm 이하
- A–D는 품질 게이트를 걸지 않고 위 표에 모두 적었습니다(비교 기준).
- 결과: `CHECK FAIL: 108 gate(s)`, 통과 428, 종료 코드 1.
  - 기존 게이트의 실패 12건은 그대로입니다(원래 클립 기준값).
  - 새 실패는 E/E2/E3의 골반·가슴 프레임 이동이 대부분입니다. 그 밖에 E2의 페이드 침하와 D 0.1 s 등의 페이드 발끝 이동이 있습니다.
  - 그대로 남겨 두었습니다. 한도를 바꾸지 않았습니다.

### 판단

- **해결된 것 (E3)**
  - 접촉 gap 0, 디딤발 이동은 원본 수준(0.013 / 0.019 m)
  - 킥 구간 침하 0 (발가락 23.5° + 골반 ≤ 0.9 cm)
  - 전환 중 침하 0 (모델을 경우별 최대 1.2–7.3 cm 올림)
- **해결되지 않은 것**
  - 11_01에서 공은 몸 중심선의 오른쪽 0.54–0.63 m에서 맞습니다. 게임은 공을 선수 정면 0.43–0.50 m에 둡니다. 그래서 그려지는 몸을 그만큼 옆으로 옮겨야 합니다.
  - 그 이동은 D를 누른 뒤에야 시작할 수 있습니다. 디딤까지 0.22–0.42 s, 접촉까지 0.33–0.53 s밖에 없습니다.
  - 그래서 골반이 원본보다 빠르게(1/60 s당 최대 Xbot 0.059–0.111 m, Soldier 0.064–0.134 m, 원본 0.053–0.055 m) 옆으로 미끄러집니다.
  - 측정상 이 이동이 원본 속도 안에 들려면 약 0.43 s 이상이 필요합니다. B(접촉까지 늘림)는 서서 D 0.2 s 이상에서 골반 이동이 원본 이하지만, 디딤발이 0.26 m 미끄러집니다.
  - 차고 난 뒤에도 몸이 선수 위치에서 0.6–0.8 m 떨어져 있습니다. 대기로 돌아가는 0.25 s 동안 Soldier는 원본 속도를 넘어(0.056–0.063 m) 돌아옵니다.
- **결론**: 이 모캡으로는 게임 타이밍 안에서 디딤발 고정, 접촉, 자연스러운 몸 이동을 모두 만족하는 방법을 찾지 못했습니다.
- **선택지**
  1. **게임 설계 변경** (승인 필요): 공을 차는 발 쪽(오른쪽 약 0.3–0.5 m)에 두고 드리블하게 합니다. 시각만 바꾸면 공 출발 위치와 어긋나고, 물리 위치를 바꾸면 게임 규칙이 바뀝니다.
  2. **슛 준비 시간 연장** (승인 필요): D 누름부터 접촉까지 0.43 s 이상이 되게 합니다. 지금은 D 0.2 s 이상 누를 때만 됩니다.
  3. **다른 킥 모션**: 공이 몸 앞쪽(디딤발 옆 0.2–0.3 m)에서 맞고, 도움닫기가 짧거나 제자리인 킥을 씁니다.
     - CMU 킥 6개는 앞 단계 측정에서 모두 발끝이 몸 중심 오른쪽 0.54–0.78 m에서 맞았습니다. 이 문제가 같습니다.
     - Mixamo의 제자리 킥(이름과 내용은 확인 못 함)이나 직접 만든 키프레임 킥은 확인이 필요합니다. 라이선스는 앞 절과 같습니다.
  4. **E3를 그대로 쓰되 페이드인 미끄러짐을 받아들이기**: 실제 기기에서 보면서 판단해야 합니다. 이 환경에서는 영상으로 보지 못했습니다.

## 게임 통합 설계 (문서만, 구현하지 않음)

### 원칙

- 게임 로직이 위치와 방향을 계속 정합니다.
  - `p.pos`, `p.y`, `p.face`.
  - 정면은 +z이고 `root.rotation.y = face`입니다.
- GLB는 보이는 모양만 맡습니다.
- 물리, AI, 조작, 온라인 동기화, 리플레이는 바꾸지 않습니다.

### 바꿀 곳

- 바꿀 곳은 `applyVisual(p,x,y,z,face,a,t,ph,spd,side)`(`index.html` 4016행)의 선수 부분 하나입니다.
  - 지금은 `p.rig.root`에 위치와 방향을 넣고 `applyPose`와 `rigLife`를 부릅니다.
  - GLB 선수라면 holder에 위치와 방향을 넣고, 클립 선택과 시간만 정합니다.
- 심판과 부심(`officials`)도 같은 함수를 쓰지만, 지금처럼 절차적 rig로 둡니다.
- 쓸 수 있는 값은 이미 동기화되고 있습니다.
  - `syncAnimState`(4003행)가 정하는 `visA`, `visT`, `visPh`, `visSide`와 `spd`는 리플레이(`recordFrame`, 3619행)와 온라인 스냅숏에 이미 들어 있습니다.
  - 그래서 데이터 형식은 바꿀 필요가 없습니다.
- 클립 시간을 `mixer.update(dt)`로 쌓기만 하면, 온라인 게스트와 리플레이에서 자세가 호스트와 어긋납니다.
  - 달리기와 걷기 클립 시간은 `visPh`(달리기 위상)로 정합니다. `action.time = 위상/(2π) × 길이`.
  - 일회성 동작은 `visT`(상태 경과 시간)로 정합니다.
  - 그 뒤에 `mixer.update(0)`을 부릅니다.
  - 상태가 바뀔 때만 크로스페이드를 씁니다.

### 상태와 클립 대응

코드에서 확인한 상태는 `A`(1310행)의 21개와 `spd`입니다. 오른쪽 열은 받아 둔 파일에 실제로 있는 클립입니다.

| 게임 상태 (코드) | 언제 | 받아 둔 파일의 클립 | 판정 |
|---|---|---|---|
| `idle` | `spd ≤ 0.35` | Soldier Idle, Xbot idle | 있음 |
| `run` (느림) | `spd > 0.35`, 걷는 속도 | Soldier Walk, Xbot walk, CesiumMan animation_0 | 있음. 속도에 맞춘 재생 배속은 측정 안 함 |
| `run` (빠름) | 달리기 | Soldier Run, Xbot run | 있음. 위와 같음 |
| `gkready` | 공 가까운 키퍼 대기 | 없음 (idle로 대체 가능) | 대체 |
| `celeb` | 골 뒤 달리기 | 없음 (run으로 대체, Xbot agree는 축하 동작이 아님) | 대체 |
| `kick` | 패스, 슛 (`visSide` = 디딤발 방향) | CMU 킥 6개를 Xbot, Soldier에 리타깃 (오른발만, `models/cmu/`) | 오른발 킥만 있음. 왼발은 반전 필요. 공과 발 위치가 맞지 않음 (위 결과) |

| `header`, `jump` | 헤더, 점프 | 없음 | **없음** |
| `tackle`, `stackle`, `slide` | 태클, 서서 태클, 슬라이딩 | 없음 | **없음** |
| `skill` | 개인기 (`visSide`) | 없음 | **없음** |
| `stagger` | 몸싸움에서 휘청 (`visSide`) | 없음 | **없음** |
| `fall` | 넘어짐 | 없음 | **없음** |

- 받아 둔 파일로 바꿀 수 있는 것은 서 있기, 걷기, 달리기뿐입니다.
- 나머지 상태에서 GLB를 숨기고 절차적 rig를 보이면 같은 선수의 모양이 갑자기 바뀝니다. 그래서 축구 동작 클립을 확보하기 전에는 통합하지 않는 것이 좋습니다.

### 그 밖에 정해야 할 것

- **팀 색과 등번호**: 지금 rig는 팀 재질(`T.mats`)과 등번호 텍스처(`rig.numMat`)를 씁니다.
  - GLB에서는 팀별로 재질을 복제해야 합니다. 두 팀과 키퍼 두 명이면 4벌입니다.
  - 등번호는 새로 붙여야 합니다.
- **정리**: `setupMatch`는 지금 `scene.remove(p.rig.root)`와 번호 텍스처 dispose만 합니다.
  - GLB를 쓰면 경기마다 `mixer.stopAllAction()`, `uncacheRoot`, 뼈 텍스처 dispose(`skeleton.dispose()`)가 더 필요합니다.
  - 형상과 재질은 공유하므로 dispose하지 않습니다.
- **rig를 읽는 다른 코드**: `controlled.rig.root.position` 등 `p.rig`를 읽는 곳이 있습니다(표식 링, 힌트 원뿔 등). 바꾸기 전에 모두 찾아야 합니다.
- **도입 방식**: 설정 토글로 한 선수(조작 선수)부터 바꿔 봅니다. 꺼져 있을 때는 지금과 완전히 같아야 하며, `anim_baseline.js compare`로 확인합니다.
